# 课程资料助教：项目方案草案（v0.1）

> 状态：讨论稿，尚未进入实现承诺。目标是先对齐业务和第一版边界，再一起决定技术方案。

## 1. 项目概述

课程资料助教面向一门具体课程，为学生提供基于课程资料的问答、作业辅导和复习支持，并为教师提供资料整理与教学内容草稿生成能力。回答应尽量引用课程资料；资料不足时说明依据不足，而不是编造结论。

项目重点不只是“把 PDF 接入向量库”，还要验证四件事：

1. 能否识别学生真正想完成的学习任务，并选择合适的处理流程；
2. 检索和回答是否受课程、用户身份、资料发布时间等权限约束；
3. 多 Agent 协作是否能产出比单次生成更可靠、可审阅的教学草稿；
4. 是否能用一组可复现的问题和指标说明系统的效果与局限。

## 2. 目标用户与业务需求

### 学生

- 想理解课程概念，希望得到贴合课程讲法并带出处的解释；
- 想完成作业，希望先得到逐步提示，而不是直接看到未开放的标准答案；
- 想查找某个知识点在哪周讲过、对应哪份资料；
- 想根据课程进度和自己的薄弱点安排复习。

### 教师

- 上传和维护课程讲义、课程大纲、作业说明、FAQ 等资料；
- 设置资料归属课程、可见角色和发布时间；
- 基于已选资料生成复习提纲、练习题或讲解草稿；
- 审核、修改后再发布生成内容。

### 助教

- 查看学生常见问题并整理 FAQ；
- 协助审核回答或教学内容；
- 只访问自己被授权负责的课程内容。

## 3. 核心业务流程

### 学生提问

1. 学生登录并选择一门自己有权限访问的课程。
2. 系统识别意图，例如概念解释、作业提示、资料定位或复习规划。
3. 系统根据用户身份、课程成员关系、资料可见范围和发布时间过滤可检索资料。
4. 检索相关片段，并生成回答；回答附资料名、页码或章节等引用信息。
5. 若证据不足、意图置信度低或问题超出课程范围，系统明确说明或追问澄清。
6. 记录必要的请求、检索来源和反馈，用于排查问题与评测；避免记录不必要的敏感信息。

### 教师生成复习材料

1. 教师选择课程、目标主题、难度和允许使用的资料范围。
2. 系统检索资料并生成带引用的大纲草稿。
3. 教学写作 Agent 根据大纲生成讲解、例子和练习题。
4. 审校 Agent 检查事实是否有来源支持、引用是否匹配、题目和答案是否一致。
5. 教师查看来源与审校提示，编辑后自行决定是否发布。

生成内容默认为草稿，不自动覆盖课程资料，也不自动发布给学生。

## 4. 意图识别与路由设计

第一版建议识别以下意图：

| 意图 | 示例 | 处理方式 |
| --- | --- | --- |
| `concept_explanation` 概念解释 | “什么是梯度下降？” | 检索课程资料，分层解释并附引用 |
| `assignment_hint` 作业辅导 | “这道题我应该从哪一步开始？” | 检查作业和答案的访问策略，给提示或追问，不默认给完整答案 |
| `material_lookup` 资料定位 | “第三周讲了什么？” | 查询指定周次或主题并返回来源 |
| `study_plan` 复习规划 | “我还有一周考试，怎么复习？” | 根据课程大纲和用户提供的时间约束生成计划 |
| `out_of_scope` 超出范围 | 与课程无关的问题 | 说明当前课程助手的范围，并引导用户调整问题 |
| `clarification_needed` 需要澄清 | “这个怎么做？” | 询问课程、题目或目标等缺失信息 |

路由输入可以包括分类标签、置信度和必要的结构化字段。低置信度时不应强行调用错误流程；应澄清或退回通用课程问答。初版可先采用模型结构化分类，并用规则处理明显的权限和状态条件，之后通过标注样本评估是否需要独立分类器。

## 5. 多 Agent 写作设计

多 Agent 先限定在“教师生成复习材料”这一条业务链路，学生问答不必一开始就多 Agent 化。

建议的职责划分：

1. **资料研究 Agent**：只从教师选定且有权访问的课程材料中找依据，输出片段、位置和相关性。
2. **大纲 Agent**：根据学习目标与检索证据组织章节结构，标明每部分引用依据。
3. **内容写作 Agent**：按大纲生成讲解、例子、易错点或练习草稿，不引入无来源的课程事实。
4. **审校 Agent**：逐条核查主张与引用、覆盖目标情况，以及练习题答案的一致性；输出问题清单，而非悄悄掩盖不确定性。

编排应保存每个阶段的输入、输出、引用和失败状态，便于教师审阅与调试。Agent 数量不是目标；如果简单流程在质量、成本或稳定性上更好，应保留简单流程。

## 6. 权限模型

### 角色能力草案

| 操作 | 学生 | 助教 | 教师 |
| --- | --- | --- | --- |
| 读取已发布课程资料 | 所属课程内 | 授权课程内 | 自己负责课程内 |
| 查询未发布资料 | 否 | 默认否 | 可访问负责课程的资料 |
| 查看标准答案 | 仅在开放后 | 按教师授权 | 可管理 |
| 上传、修改课程资料 | 否 | 按授权 | 可管理负责课程 |
| 生成教学材料草稿 | 否 | 可按授权协助 | 可生成和审核 |
| 发布教学材料 | 否 | 默认否 | 可发布 |
| 查看其他学生的提问记录 | 否 | 最小必要范围 | 课程范围内、仅用于教学管理 |

### 权限执行原则

- 权限在服务端校验，不能依赖前端隐藏按钮。
- 检索阶段就按课程和可见策略过滤资料；不能先检索出无权内容，再寄希望于提示词让模型忽略。
- 生成和缓存结果也要绑定用户、课程和资料权限范围，避免不同角色间复用越权结果。
- 对答案开放时间、退课、教师撤回资料等状态变化，定义明确的生效规则。
- 对拒绝访问和越权检索建立审计事件，不在普通日志中泄露正文或密钥。

## 7. 第一版（MVP）范围

### 做

- 单门课程、少量用户角色（学生和教师；助教权限可先沿用教师授权子集）；
- 上传 PDF 与 Markdown 课程资料，记录课程、资料类型、可见范围和发布时间；
- 文档解析、分块、索引和删除/重新索引的基本流程；
- 学生提问：先支持概念解释、资料定位和作业提示三种意图；
- 回答附可核对的资料来源；证据不足时拒答或澄清；
- 服务端课程权限校验和检索前过滤；
- 教师基于课程资料生成复习提纲草稿，教师确认后再复制或发布；
- 一份小型评测集，用于检查意图路由、检索命中、引用和权限边界。

### 暂不做

- 多学校、多租户的复杂组织体系；
- 自动评分、自动批改并给出最终成绩；
- 自动发布 AI 生成内容；
- 复杂长期记忆、开放式 Agent 自主调用任意工具；
- 多模态课件解析、实时课堂录音；
- 第一版就追求海量数据和高并发部署。

## 8. 评测与验收

先准备约 30–50 条人工编写或审核的问题，覆盖概念、作业提示、资料定位、模糊问题、超范围问题和权限边界。这个数量是起步建议，后续根据课程覆盖面调整。

建议记录以下指标：

- **意图识别**：各类别准确率、混淆情况，尤其是作业求助与概念解释的混淆；
- **检索质量**：Top-k 结果中是否包含标注的依据片段，可统计 Recall@k；
- **答案质量**：答案是否由引用支持、是否回答了问题、证据不足时是否正确拒答；
- **权限安全**：越权资料是否进入检索结果或回答；该项应以测试用例零泄漏为目标；
- **写作质量**：引用准确度、学习目标覆盖、题目与答案一致性，以及教师修改量；
- **工程指标**：接口成功率、响应耗时和单次生成成本。

第一版不把某个未经验证的分数写成承诺。先建立基线，记录模型、提示词、检索参数和数据集版本，再比较改动前后的结果。

## 9. 技术模块草图

```text
FastAPI
├── 身份认证与课程权限
├── 意图识别与请求路由
├── 资料管理与解析
├── RAG 检索与答案生成
├── 教学内容 Agent 工作流
├── 评测、反馈与审计日志
└── 持久化层（用户、课程、资料元数据、任务记录）
```

具体模型供应商、向量数据库、认证方式和前端框架留待调研后确定。选型时优先考虑本机可运行、文档清晰、便于替换和能解释设计取舍。

## 10. 开发阶段建议

1. **业务与数据准备**：确定一门课程、资料来源、资料授权方式和示例问题。
2. **最小 RAG**：完成资料解析、检索、带引用回答和无依据拒答。
3. **意图路由**：加入结构化意图识别、澄清流程和路由评测。
4. **权限闭环**：加入用户、课程、资料范围校验，并覆盖越权测试。
5. **教师写作工作流**：实现复习提纲生成、审校提示和人工发布流程。
6. **展示与复现**：整理 README、架构图、评测结果、演示数据和部署方法。

## 11. 开始开发前待确认

- 选哪一门课程作为演示场景？当前 `sources/` 中的 PDF 是否属于这门课程、是否有权用于公开演示？
- 第一版使用公开或自编材料，还是只在本地使用已有课程资料？
- 作业辅导要采用“提示优先”，还是允许对已结束作业展示完整解析？
- 演示时是否需要真实登录，还是先用可切换的演示角色展示权限？
- 模型服务预算、数据能否发送到第三方 API、是否需要本地模型？

这些问题确认后，再把方案收敛成实现任务和数据模型。
